# Benchmark methodology

This file fixed the method before any number existed, so that a result could not be shaped after
the fact. The procedure below is unchanged since then; the results it governs are in
[RESULTS.md](RESULTS.md), with the raw reports committed beside them.

Nothing in this directory, the README, or any commit message may quote a throughput or latency
figure that was not produced by the procedure below and recorded with its full environment.

## Procedure

1. Build **Release** (`-O2`/`-O3`, sanitizers off). A sanitizer build is never a throughput
   measurement.
2. Benchmark on Linux only. It is the supported platform
   ([ADR-004](../docs/decisions/ADR-004-linux-is-the-supported-platform.md)) and the one whose
   barrier is `fdatasync(2)`; a macOS `F_FULLFSYNC` number measures a stronger barrier and must
   never be published beside a Linux one.
3. Record, with every result: compiler and version, CPU, RAM, OS and version, filesystem type,
   storage class, the durability barrier actually used (ADR-001), and machine load.
4. Use a fresh file per trial in a dedicated scratch directory. Equal payload contents and record
   counts across policies, generated by the deterministic payload stream so every policy writes
   identical bytes.
5. Workloads: 64, 512, and 4096-byte payloads; 10,000–100,000 records per trial within the time and
   disk budget.
6. Policies: `sync_each`, `sync_batch(16)`, `sync_batch(64)`, and optionally `write_only` labelled
   **accepted, not durable**. For `write_only`, durable-ack latency is *not applicable* and must be
   reported as such rather than as a number.
7. At least five trials per data point. Report median and spread (min/max or interquartile range),
   never the best run.
8. Metrics: acknowledged records/sec, total wall time, p50/p95/p99 **durable acknowledgment latency
   at the policy's actual acknowledgment granularity**, bytes written, and peak RSS where available.
9. Compute any comparison against the `sync_each` baseline only *after* measuring. No target
   speedup is assumed, and batching may help far more or far less than expected depending on the
   filesystem's sync semantics.
10. Explain OS page-cache effects. Do not compare any of this to real power-loss persistence.

Benchmarks are reports, not CI gates: CI stays deterministic and lightweight. The test suite
exercises `bench` with tiny workloads and asserts syscall counts and report structure, never a
duration. Raw output from ad-hoc runs belongs in an ignored `out/`; the curated example in
[RESULTS.md](RESULTS.md) and its `results-*.json` are committed because they have actually been run.

`eventlog bench` enforces most of the above rather than trusting anyone to remember it: a report
states whether it may be quoted, percentiles are nearest-rank so every figure is an observed sample,
there is no way to ask for the best trial, and a run whose policies did not write identical bytes or
whose barrier calls did not match its acknowledgment granularity fails instead of reporting
([ADR-008](../docs/decisions/ADR-008-write-only-and-benchmark-honesty.md)).
