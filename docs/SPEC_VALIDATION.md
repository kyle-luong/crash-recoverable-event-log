# Specification validation — CPP-00 … CPP-04 (Milestone 1)

Gate defined in `00_SHARED_AGENTIC_ENGINEERING_WORKFLOW.md` §3 ("Specification-first gate").
Reviewed against `docs/PRD.md` on 2026-09-08 before any implementation.

**Outcome: `spec-ready`**, with four resolutions recorded below. No PRD acceptance criterion was
weakened, and no `MUST` was reinterpreted. Two resolutions became ADRs because they fix a
fundamental guarantee or a data-format-adjacent behavior.

## 2. Resolutions

### R1 — `fdatasync` is not available on the development host (→ ADR-001)

The PRD targets Linux/POSIX and names `fdatasync(2)` as *the* durability contract. The development
host is macOS/arm64, where `fdatasync` is not part of the public API and plain `fsync` does **not**
flush the drive's volatile write cache.

Resolution: a single `FileOps::SyncData` boundary maps to `fdatasync` on Linux and
`fcntl(F_FULLFSYNC)` on macOS (falling back to `fsync` only when the filesystem rejects
`F_FULLFSYNC`). The acknowledgment rule is unchanged — a record is durable only after that call
returns success. The platform actually used is recorded in every benchmark and crash-test result,
because the two primitives have materially different cost and different guarantees. This does not
alter any acceptance criterion; it makes the one named syscall a documented per-platform mapping.

### R2 — Structurally invalid *complete* header: incomplete tail or hard corruption? (→ ADR-002)

The PRD says an incomplete trailing record is recoverable and a "fully formed" corrupt record is
not, but it does not classify a trailing record whose 24 header bytes are all present and whose
magic/version/flags/length are invalid. The two rules could each be argued to apply.

Resolution: classified as **hard corruption** (`corrupt_complete_record`), not a recoverable tail.
Justification is the supported fault model: under single-writer process termination the trailing
bytes are always a strict byte-prefix of the encoded record, because `write(2)` copies from a
caller buffer and a `SIGKILL` can only stop the write loop between calls. A prefix shorter than 24
bytes is reported as an incomplete header; a prefix of 24 or more bytes therefore carries the
genuine header. A fully present but invalid header is evidence of damage outside the supported
model, so truncating it would be exactly the "silent acceptance of arbitrary corruption" the PRD
forbids.

### R3 — Deterministic payload content for `append` is unspecified

PRD §3 requires "synthetic deterministic records" but defines no byte content, which would make
`append` output non-reproducible across machines and make benchmark comparisons unverifiable.

Resolution: payloads are generated by a documented SplitMix64 stream keyed by sequence number and
serialized little-endian, so the same `(sequence, payload_bytes)` pair yields identical bytes on
any platform. Specified in `README.md` and implemented in `src/payload.cpp`. This is an addition
of detail, not a change to a requirement.

### R4 — Durability of a newly created log file's directory entry

The PRD never mentions syncing the parent directory. Syncing only the file descriptor leaves the
new file's *name* in a possibly unflushed directory block, so a first record could be acknowledged
durable while the file itself is not guaranteed to be reachable after a crash.

Resolution: on creating a new log file, the containing directory is opened and synced once before
any record can be acknowledged. Required to make the existing CPP-AC05 acknowledgment claim true
rather than to extend it.

## 3. Deferred, with reason

These PRD items are in scope for the project but out of scope for Milestone 1. They are specified
clearly enough to implement and are not blocked:

- `sync_batch(N)` ack boundaries and `fdatasync` failure handling (CPP-05) — M2.
- Scriptable `FileOps` fault injection exposed beyond unit tests (CPP-06) — M2. Milestone 1 already
  needs injection for CPP-T04/T05, so a narrow test double exists now.
- Process-crash supervisor and the acknowledged-prefix oracle (CPP-07) — M3.
- Release benchmark and JSON metrics (CPP-08) — M4.

## 4. Open question for the human (non-blocking)

`write_only` is specified as diagnostic-only and must never carry a durable acknowledgment.
Milestone 1 implements the policy enum but intentionally leaves `write_only` unimplemented, so no
code path can report it as durable before the benchmark milestone defines its reporting. Confirm
this is the intended ordering when M4 is planned.
