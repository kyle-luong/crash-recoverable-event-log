## Done

Record format v1, frozen and pinned by fixed golden byte vectors generated by an independent
implementation. Explicit little-endian serialization; nothing in the format path depends on host
endianness or struct layout.

`sync_each` writer: RAII descriptor, short-write loop retrying only `EINTR`, advisory `flock` for
cooperating writers, directory fsync for any log that holds no records yet, and a terminal failure state after any failed
write or sync (ADR-003). `durable_through_sequence` advances only after the durability barrier
returns success; `accepted_through_sequence` is tracked separately and never conflated with it.
Resuming an existing log syncs its prefix once at `Open` rather than inferring durability from the
records being present (see *Contract review* below).

Log scanner reporting `clean` / `incomplete_tail` / `corrupt_complete_record` /
`sequence_violation` with a byte offset and a human-readable detail string. Recovery with a
read-only preflight and opt-in `--truncate-tail` that discards only a structurally incomplete
trailing record (ADR-002), refuses symlinks, holds the writer lock, re-checks the file against the
preflight, and syncs the shortened length.

`sync_batch` writer (M2): `AppendBatchAndSync` encodes N records into one contiguous buffer,
issues one `write`, issues one barrier call, and acknowledges the whole batch only afterward
(ADR-006). Batches are explicit calls rather than hidden buffering, so nothing is left
accepted-but-unsynced between calls and `Close()` has no partial batch to resolve. A failed write
or sync acknowledges no record in the batch and is terminal. Batch bounds (`batch_size`,
`kMaxBatchRecords`, `kMaxBatchBytes`) are all checked before the batch buffer is allocated.

`WriterStats` counts write calls, barrier calls, acknowledgment units, records and bytes, so the
batching tradeoff is checked by assertion instead of prose: `sync_batch(32)` performs one write and
one barrier call where `sync_each` performs 32 of each, and both produce byte-identical files.
These are counts, not timings. Timings are measured separately by `bench` and recorded with their
environment in `benchmarks/RESULTS.md`; no test asserts a duration.

Crash harness (M3): `eventlog crash-test` spawns a writer as a child process, stops it with
`SIGKILL` at one of six instrumented checkpoints, recovers the log, and checks it against the
acknowledgments the supervisor recorded in its own memory *before* issuing the kill (ADR-007). The
child parks at its checkpoint and announces it, so the kill lands on a known state rather than a
guessed one, and a seed replays the same matrix. The acknowledged-prefix invariant is checked in one
direction only: every acknowledged record must be present, while valid records that were never
acknowledged are permitted and counted. Recovered records are read back and compared byte for byte
against the deterministic payload for their sequence, so a structurally perfect record that is not
the one that was written is caught. Hard corruption is a violation, never truncated.

Benchmark (M4): `eventlog bench` compares `sync_each`, `sync_batch(16)`, `sync_batch(64)` and
`write_only` on one workload over N trials with a fresh file each time, and writes a JSON report
carrying its full environment and units. It reports median and range, never the best run;
percentiles are nearest-rank, so every figure is a latency that occurred; and it fails rather than
report a run whose policies did not write identical bytes or whose barrier calls did not match its
acknowledgment granularity. Every report stamps `publishable`, true only for a Release build with
sanitizers off on Linux, and the table prints the disqualification as a banner above the numbers
(ADR-008).

`write_only` (M4): accepted, never durable. It has its own method returning a type with no
durability field at all, calls the barrier nowhere — not per record and not when resuming an
existing log — and leaves `durable_through_sequence()` at 0 for the writer's life. The crash harness
rejects it, so it cannot enter the acknowledged-prefix claim.

Hardening (M5): the read path now goes through the injectable `FileOps` boundary, so an I/O error
while reading is provably reported as an I/O error and never as a verdict about the log's contents.
A log must be a regular file, checked on the descriptor rather than the path, with `O_NONBLOCK` on
every open so a named pipe is refused instead of blocking for a peer that never arrives. Both
commands that write a report — `verify --json` and `bench --out` — refuse a symlink and refuse to
replace existing content without `--overwrite`, checked before the command does any work so a
refusal can never be mistaken for a verdict.

CLI: `append` (with `--policy sync_batch --batch-size N` or `--policy write_only`), `verify`,
`recover`, `crash-test`, `bench`, with the PRD's exit codes and `verify --json`.

Eight ADRs fix the decisions that pin a guarantee or the workflow: the durability barrier
(ADR-001), the recovery classification boundary (ADR-002), terminal sync failure (ADR-003), Linux as
the supported platform (ADR-004), main-first development (ADR-005), the batch acknowledgment
boundary (ADR-006), the crash supervisor's kill protocol and oracle (ADR-007), and the shape of a

## Contract review (2026-10-29)

An independent re-read of the durability and recovery contracts against the implementation. One
substantive defect, now fixed; four observations recorded rather than changed.

**Fixed — `Open` reported resumed records as durable without ever syncing them.** The writer set
`durable_through_sequence` to the last sequence found by scanning an existing log. A scan reads
through the page cache, so it proves only that those records are present and structurally complete,
never that any of them reached the durability barrier. A writer killed between `write(2)` and its
sync leaves a log that scans identically to a fully synced one, and `write_only` produces that
state by design. `Open` now issues one `SyncData` before reporting the resumed prefix as
durable, and fails with `kUnknownDurability` if that call fails. Three tests pin it:
`ResumeSyncsTheExistingPrefix`, `ResumeFailsOpenWhenTheSyncFails`,
`FreshLogSyncsItsDirectoryEntryAndNoDataAtOpen`.

Checked and found correct, recorded so the reasoning is not re-derived:

- **`fdatasync` after `ftruncate` does persist the shortened length.** `fdatasync(2)` omits only
  metadata not needed to read the data back, and `st_size` is explicitly not in that category, so
  `ApplyRecovery` needs no separate metadata sync.
- **No integer overflow in the payload-length path.** `payload_length` is `uint32_t` and
  `total_size()` widens to `uint64_t`, so the bound check cannot wrap; the 1 MiB limit and the
  bytes-remaining check both precede any allocation.
- **`O_APPEND` with `::write` is consistent.** `FileOps::Write` uses `write(2)`, not `pwrite(2)`,
  so the offset carried alongside it is diagnostic only and cannot disagree with where bytes land.

Known limits, unchanged:

- `ScanLog` constructs `PosixFileOps` directly, so read-path I/O errors are not fault-injectable.
  Worth routing through the injected `FileOps` when M3 needs it.
- `ApplyRecovery`'s stale-plan guard compares file size only. An in-place modification of the same
  length between preflight and apply would not be detected. The writer lock is taken after the
  preflight scan, which is the window; a re-scan under the lock would close it.
- `WriteFully` and `ReadAt` retry `EINTR` without a bound, as PRD §3 specifies. Unbounded in
  principle; `EINTR` does not occur for regular-file I/O in practice.
- Scanning uses two `pread` calls per record. Correct, and fine at current sizes. The M4 benchmark
  measures the append path only, so no verification-throughput figure exists to be wrong; one would
  need measuring before it could be quoted.

### The one correctness caveat left, with its severity

**Narrowed on 2026-11-12.** A previous version of this section argued that a stale plan could not
discard a valid record, because `truncate_to` ends a prefix that was valid when the plan was made
and "a same-length edit cannot make that prefix longer". That reasoning holds for an edit **in
place**. It did not hold for a *different file* of the same length appearing at the path, which can
have a longer valid prefix — so applying the stale target to it would have discarded a complete
record, the one thing ADR-002 forbids outright. The independent audit found that hole.

`ApplyRecovery` now compares the file's **identity** (device and inode, read from the descriptor it
holds under the lock) as well as its length, against the identity `PlanRecovery` captured *before*
it scanned. A replaced, renamed or recreated file is refused with "is no longer the file the
preflight examined". `PlanIsRejectedWhenTheFileWasReplacedAtTheSameSize` pins it with a real
replacement at a byte-identical length, so the length check cannot be what rejects it.

What remains is narrower: an **in-place** modification of the same file, at the same length, inside
the window between the preflight and the lock. Same inode, same size, so neither check sees it.

Why that remainder is a caveat and not a defect to fix in a hurry:

- It needs a **non-cooperating** writer. A cooperating one cannot do it — appending changes the
  size, and it cannot hold the lock. PRD §3 says explicitly not to claim a guarantee against
  processes that ignore `flock`, so this is outside the stated contract.
- The failure mode is not data loss, and here the original reasoning does apply: an in-place edit
  cannot lengthen the valid prefix, so truncating to the stale `truncate_to` can only leave a
  damaged record in place, reported with counts from the stale plan, and the next `verify` catches
  it. It cannot discard an acknowledged record.
- Closing it needs the scan and the truncation to share one descriptor, which means `ScanLog`
  taking an `fd` rather than a path. That is a signature change across the read path for a trigger
  that is out of scope.

None of this makes concurrent modification safe, and nothing here claims it does: the identity check
rejects a stale plan, and this project still supports one writer at a time (PRD §2).

## Crash harness notes (2026-11-12)

Design decisions are in ADR-007. What is worth carrying forward separately:

**The oracle is tested, not just used.** A supervisor that prints `Violations: 0` proves nothing
unless the check behind it can fail, so `tests/test_crash.cpp` runs the oracle against logs damaged
on purpose — a missing acknowledged record, a flipped byte in a complete record, a sequence gap, a
payload that is valid but is not the one written, a torn tail from a writer that exited normally —
and requires each to be reported. The path from a detected violation to exit 1 is covered through
the CLI by `--child-program`, pointing the supervisor at `tests/fake_crash_child.sh`, which claims
an acknowledgment for a record it never wrote. That seam exists for exactly this test.

**Two assertions in `cli_tests.sh` are invariants of the design, not of a seed.** Every `mid_write`
run must leave exactly one recoverable tail, because the scenario generator never places the stop on
a record boundary; and no other checkpoint can leave a tail at all, because each stops either before
the write begins or after it completed. So `Incomplete tails recovered` must equal the `mid_write`
count in any sweep. Checked across six seeds by hand before the assertions went in.

**`before_write` and `after_ack` must show zero extra unacknowledged records**, while
`after_write_before_sync` and `after_sync_before_ack` must show a nonzero count. Those four facts
are what distinguish a checkpoint that fired from one that silently did nothing, which a bare
`Violations: 0` cannot.

Known limits, recorded rather than fixed:

- If a child neither parks nor exits, the supervisor blocks in `read` until the CTest timeout. That
  is a hang rather than a reported failure. No scenario produces it, and adding a timeout would mean
  `poll`/`alarm` plumbing for a case that has not occurred.
- The `--workdir` symlink check tests the final path component. Everything the harness writes lives
  inside the subdirectory it creates itself, and only that subdirectory is removed.
- `ScanLog` still constructs `PosixFileOps` directly, so read-path I/O errors remain outside fault
  injection. M3 did not need it: the harness checks logs on disk through the normal read path.
- `ApplyRecovery`'s stale-plan guard still compares file size only. The harness reaps the child
  before recovering, so nothing can modify the file inside that window here.

## Benchmark notes (2026-11-12)

Design decisions are in ADR-008. The measured results, with the environment they came from, are in
`benchmarks/RESULTS.md`, and the raw reports are committed beside it. What matters for the next
person:

**The spread is the headline, not the medians.** On the machine measured — a Docker Desktop
`linuxkit` VM on an Apple-silicon host, ext4 on a virtual disk, host not idle — the durable policies
varied by up to **4.3× between the slowest and fastest trial of the same workload**, while
`write_only` varied by at most 1.06×. That contrast localises the noise to `fdatasync` rather than
the record path. So the committed figures bound an order of magnitude and nothing finer: batching
bought 9.2× to 84.6× the `sync_each` throughput, and the places where that is non-monotonic across
payload sizes sit inside the spread. Five trials is the documented minimum and is visibly not enough
on this hardware. `RESULTS.md` leads with this before showing a number.

**Batching does not reach its batch size, and ack latency does not improve.** `sync_batch(64)`
reached 35× the baseline at 64-byte payloads, not 64×; amortising a barrier is not removing it.
Median per-acknowledgment latency rose with batch size at two of the three payload sizes, because
one acknowledgment now covers N records. Throughput and ack latency pull against each other, which
is what a batch size actually chooses between.

**The honesty rules are enforced in code, not by discipline.** There is no accessor for the best
trial; percentiles are nearest-rank so no reported latency was ever interpolated; the run fails if
the policies did not write byte-identical files or if a durable policy's barrier calls did not equal
its acknowledgment count. Those checks exist because every one of them is a way a benchmark can
quietly stop comparing what it claims to compare.

**Unmeasured, deliberately.** Nothing here measures bare metal, cloud storage, power-loss
persistence, or the verify/recover read path. `storage_class` is reported as `unknown` rather than
guessed from device names, because a wrong guess silently changes how every number should be read.

**Two defects in my own tests, caught by the gate.** The first draft of `test_bench` asserted that
the environment it captured was *not* publishable, on the reasoning that the suite is built with
sanitizers. It is — in two of the three `verify-full.sh` phases. The third builds Release with
sanitizers off, where the correct answer is the opposite, so three cases inverted. The fix was not
to special-case the phase but to expose the rule as `IsPublishable(build_type, sanitizers,
supported_platform)` and check its whole truth table, which a suite can do regardless of its own
build, plus a table test built from a hand-made report so both the warning and the no-warning branch
are covered everywhere. The `cli_tests.sh` equivalent now asserts that the table and the JSON *agree*
about publishability rather than asserting which answer they give. That is a better test than what
it replaced: the original could only ever have checked one row.

**A regression I introduced and then measured out.** M5 first added
`detect_stack_use_after_return=1` to the sanitizer options alongside `strict_string_checks` and
`_GLIBCXX_ASSERTIONS`. The Linux gate failed: the exhaustive recovery sweep timed out after 300 s,
having taken 5.48 s before. The ratios were the clue — `cli_tests` slowed only 1.7× because it is
dominated by `fsync` wall time, while the sweep slowed more than 55×.

Measured on Linux rather than guessed: the sweep takes **10.7 s without that one option and over
420 s with it**, a factor of more than 39. In a Debug build nothing inlines, so every call allocates
an ASan fake stack frame, and `ExerciseEveryTailCut(4096, 2)` performs on the order of 34 million
trivial container operations across its 4119 iterations.

It is now off by default, with the measurement and the re-enable command recorded in
`scripts/sanitizer-env.sh`. Two things worth being clear about. This is not a weakened gate:
CPP-AC14 asks for ASan/UBSan, which is satisfied, and the dropped option was an M5 addition of mine
rather than part of any criterion — the bug class it adds is a returned reference to a local, and
this code returns `Result<T>` by value throughout. And the timeout was left at 300 s on purpose: it
exists to catch a hang, not to enforce a performance budget, so raising it would have hidden the
regression instead of removing it.

**One Linux-only defect, caught by the gate.** `struct ::utsname info{}` and `struct ::rusage
usage{}` formatted differently under clang-format 14 (Debian, the supported platform) than under 17
(Apple), which Apple clang's local run could not see. Fixed with the same local-alias pattern
`PosixFileOps::FileSize` already used for `struct ::stat`, and the comment there now points at this
one. That makes four defects the Linux gate has caught that macOS never reported, which is the
argument for ADR-004 restated in practice.

## Hardening notes (2026-11-12)

No ADR: none of this decided anything the PRD had left open. It closed gaps.

**An I/O error is not a verdict about the log.** `ScanLog` answers "what shape is this log" and
reserved Errors for "I could not find out" — but the read path constructed `PosixFileOps` directly,
so that distinction had no test. It was the one deferred item that mattered, because confusing the
two is the worst wrong answer this tool can give: a failing disk reported as corrupt data sends
someone to the wrong problem, and a user told their log is damaged may throw it away. `FileOps`
gained a `ReadAt`, `ScanLog` and `LogReader::Open` take an optional one, and five cases in
`test_reader` now pin the behaviour — a failed first read, a failed read after a valid header is
already decoded, a failure partway through a multi-record scan, short reads being looped over rather
than mistaken for end of file, and `LogReader::Next` surfacing the same error.

**A log must be a regular file.** The format is read with `pread(2)`, sized with `fstat(2)` and
shortened with `ftruncate(2)`; none of those mean anything on a directory, a device or a pipe, so
this is a correctness requirement rather than a policy. Checked on the descriptor, so nothing can be
swapped in between the check and the open. `O_NONBLOCK` is on every log open for one reason: opening
a named pipe for writing would otherwise block until a reader appeared, so the tool would hang on a
path it should refuse. The flag has no effect on a regular file, which is the only thing that gets
past the check.

**The README was verified, not reviewed.** Every documented command was re-run on Linux Release and
its output diffed against the file. All of it matched except one thing: the `sync_each` append
example had silently dropped its third output line (`Acknowledgments: 1000  Barrier calls: 1000
Write calls: 1000`) while claiming to be real output. Fixed, and the claim is now explicit about
which blocks are measured and that nothing is illustrative. Two stale descriptions went with it: the
layout section listed seven headers when there are fourteen, and the line "file_ops.cpp is the only
POSIX boundary" had stopped being true once the crash harness started calling `fork`/`exec`/`kill`
and the benchmark started reading the environment. That sentence is now specific about what goes
through `FileOps` and what does not.

## Independent audit remediation (2026-11-12)

No ADR: nothing here decided anything the PRD had left open. Two items corrected code that was
narrower than its own documentation, one corrected an exit code, one closed a hole in a guard, and
the rest removed code. The audit that found them is the review item 8 of the definition of done had
been waiting for; it re-ran `verify-linux.sh` and the 300-scenario gate itself rather than taking
the previous evidence on trust, and it confirmed the acknowledgment boundary, the recovery
classifications and the supervisor's oracle as correct.

**Fixed — the directory entry was never synced for a log this tool did not create.** `Open` synced
the containing directory only when its own `open(O_EXCL)` had created the file. A file that already
existed but was empty passed both guards: `file.created` was false and `size > 0` was false, so no
directory sync ever happened for that log, by anyone. `touch events.log && eventlog append` is
ordinary use and needs no flag, and it acknowledged records whose file name had never been flushed.
ADR-001 and `docs/SPEC_VALIDATION.md` R4 both state the wider rule, so the code was narrower than
the documents rather than the documents being wrong. The guard is now `file.created || size == 0`.
Only power loss could ever have exposed it — under a process crash the directory entry is in the
page cache — so no claim this project makes was false. Both documents now state the implemented
trigger, and ADR-001 records the amendment.

**Fixed — that directory sync had no test at all.** It was the one durability step in the project
with nothing that could fail if it broke: `ScriptedFileOps` had counters and failure injection for
writes, syncs and reads, and nothing for `SyncDirectory`. The test whose comment claimed to cover it
asserted only that no *data* sync happened. Deleting the call outright would have kept the suite
green, which is why the defect above survived five milestones. `ScriptedFileOps` now counts
directory syncs and can fail them, and three cases pin the behaviour:
`FreshLogSyncsItsDirectoryEntryAndNoDataAtOpen`, `ExistingEmptyLogStillSyncsItsDirectoryEntry` and
`OpenFailsWhenTheDirectorySyncFails`. Each new case was checked against a build with the fix removed
and fails there, so none of them is vacuous.

**Fixed — an out-of-range `--batch-size` reported the wrong exit code.** `--records` and
`--payload-bytes` are parsed with their real bounds and exit `64`, and so does the batch *buffer*
bound on the adjacent line of `cli_tests.sh`; `--batch-size` alone was parsed with a ceiling of
`1 << 20`, passed parsing, and failed later inside `Open` as a runtime error (`10`). It is now
parsed with `kMaxBatchRecords`. PRD §3's table says only "nonzero on I/O/contract error" for
`append`, so both codes satisfied the PRD; what the old behaviour contradicted was the README's own
exit-code table, which assigns `64` to "invalid arguments" and `10` to an "I/O or contract error".
An out-of-range bound is an invalid argument, so `64` is the documented code. One existing `cli_tests.sh` assertion encoded the old
code and was updated to `64`; it still asserts a refusal with its message, so nothing was weakened.
`sync_batch --batch-size 1` keeps exit `10`: that is a policy-coherence error caught in `Open`, not
an out-of-range number.

**Closed — the stale-plan guard could be satisfied by a different file.** Evaluated first, as asked:
a same-length *replacement* is not realistically reachable inside the supported model, which is one
cooperating writer and no concurrent modification (PRD §2). It needs a second process to delete and
recreate the log at the same byte length inside the window between `PlanRecovery` and
`ApplyRecovery`'s lock. It was fixed anyway because the guard is cheap and the outcome it prevents —
silently discarding a complete valid record — is the single thing ADR-002 forbids without
qualification. `IdentifyFile(fd)` returns device and inode; `PlanRecovery` captures it *before* the
scan, so the recorded identity is never newer than the scan it belongs to; `ApplyRecovery` compares
it on the descriptor it holds under the lock. See *The one correctness caveat left* for what this
does and does not cover. It rejects a stale plan. It does not make concurrent modification safe.

**Simplified.** `FileDescriptor::release()` deleted — unused everywhere, and it handed out a raw
descriptor, which is the one escape hatch the project's "no bare `close()` in logic code" rule
exists to prevent. `kMaxRecordSize` deleted — unused. `EncodeHeader` moved out of `record.h` into
the anonymous namespace of `record.cpp`, its only caller. The per-record header is now laid down
once instead of twice: `EncodeHeader` used to fill the 24-byte prefix and then call
`ComputeRecordCrc`, which filled its own second copy of the same bytes purely to checksum them; it
now checksums the bytes it just wrote. `ComputeRecordCrc` stays public because the read path and
`test_codec` both need it from header fields alone. Output is byte-identical, which the golden
vectors and `sync_batch`/`sync_each` file comparison both confirm. The `eintr_rounds` comment in
`ScriptedFileOps` was corrected: the counter is a lifetime total, not per write, and a future test
written from the old comment would have passed for the wrong reason.

**Left open, deliberately, with the benefit judged too small.** Both were offered by the audit and
declined rather than missed:

- `verify --json` writes no report when the log's format version is unsupported. The exit code is
  correct (`2`), the message is on stderr, the bytes are preserved, and the README never promises a
  report for every verdict. A `ScanReport` cannot carry the verdict either, because PRD §4's result
  classes do not include one — so the honest fix is documentation, which this entry is.
- `WriteFully` and `ReadFullyAt` retry `EINTR` without a bound. `write(2)` on a regular file does
  not return `EINTR` repeatedly, so this is unreachable in production; a `FileOps` double that
  always returned it would hang until the 300-second `ctest` timeout. The 3-attempt no-progress
  guard already covers the reachable case.

**Item 8 was the one gap, and it is now closed.** A previous version of this file argued that no
further work by the author could close it: self-review cannot find the class of error where a
specification is misread consistently, because the same misreading writes the code and the test that
confirms it. `docs/00_SHARED_AGENTIC_ENGINEERING_WORKFLOW.md` §0 names a fresh-context model for
exactly this, and the highest-value targets were listed as the acknowledgment boundary in
`writer.cpp` against PRD §3, the classification boundary in `reader.cpp` against PRD §4's result
classes, and the crash supervisor's assumption that a parked child plus `SIGKILL` models a process
crash faithfully (ADR-007).

That review was carried out on 2026-11-12 by a fresh-context session that had no part in writing
this code, against those three targets plus the stale-plan guard. It re-ran the verification rather
than trusting it, and it confirmed the core: `durable_through_` advances in exactly one place, the
recovery classifications match ADR-002 line for line, the supervisor's oracle is independent of the
log and demonstrably able to fail, and the process-crash/power-loss boundary is drawn correctly
throughout. It also found three real defects that self-review had missed — see *Independent audit
remediation* below. The owner reviewed the findings and approved the remediation, which is the human
approval ADR-005 substitutes for the clause's "human merges".

Item 8's second clause, "human merges", predates the move to main-first (ADR-005), which replaced
merging with human approval of consequential changes. The clause has not been reinterpreted here; it
is recorded as superseded by that ADR rather than as satisfied.

## For the owner — acted on, not asked

Neither item below blocked anything. Both are recorded so a decision made by following the
documents can be overturned deliberately rather than discovered later.

1. **`write_only` was implemented in M4**, which is where `docs/PLAN.md` had always placed it. The
   open question in `docs/SPEC_VALIDATION.md` §4 asked only about that ordering, never about the
   policy's meaning, which PRD §2 and §3 already fix normatively. Its shape is ADR-008: a separate
   method, a result type with no durability field, no barrier call anywhere, and continued exclusion
   from the crash harness. If a different ordering was intended, ADR-008 is the decision to revisit,
   and the policy can be refused at `Open` again without touching anything else.

2. **The committed benchmark figures come from a virtual machine.** Docker Desktop's `linuxkit` VM
   is the only Linux available here, and ADR-004 makes Linux the platform whose numbers count. The
   environment block records it, and `RESULTS.md` says plainly that a virtualised `fdatasync` is a
   different cost from a real one. The numbers are honest about what they measured; they are not a
   statement about bare metal. A run on quiet physical Linux with more trials would replace them
   with stable figures, and nothing in the repository depends on the current ones being precise.

A previous version of this file stated that
